# Reliability and performance changes

Ubuntu PostgreSQL now owns profile reads and owner roles as well as trading and research. Supabase continues to handle login, Auth and user metadata. Only the allowed profile columns mirror to its profiles table. No trading data, credentials, orders, market history or research payloads are included in that mirror.

The writer applies additive migration `014_local_profiles.sql` on startup. The first successful background discovery imports trusted Supabase profiles, including existing owner roles. Ordinary profile reads then use PostgreSQL. An existing local row remains usable during Supabase outages; an uninitialized identity must obtain its trusted profile before backend access. User-editable Auth metadata cannot grant owner privileges. Discovery checks for newly registered profiles every five minutes and does not overwrite established local authority.

Authenticated users can update `display_name`, `avatar_url` and `phone_number` with `PUT /api/profile`. Only an existing owner can change `user_type` through `PUT /api/owner/users/{id}/role`. Local SQL edits of a profile's `data` also queue mirroring through a database trigger. Change owner roles locally after cutover; edits made only in the Supabase dashboard do not override an established local profile. Auth account/password/user-metadata management remains in Supabase.

Local edits commit before synchronization. The durable pending revision coalesces repeated updates, survives restarts, backs off after remote failures, and cannot acknowledge a newer local edit with an older in-flight mirror result. Unchanged API saves do not create new pending revisions. Private `/health` includes profile-sync pending counts and diagnostic codes.

Execution still groups shared-wallet aliases together and bounds concurrent account groups at the existing configured limit. Risk evaluation now has its own scheduler task, so slow entry/exit batches do not postpone checks on unrelated accounts. Operations for one account group remain coordinated. Idle sessions close periodically; shared rate histories survive session cleanup for their full five-minute window. Product metadata and wallet display caches are bounded.

Recovery admission is stored in PostgreSQL. Entry, attention reconciliation and subaccount release each have a maximum of five automated attempts with increasing delays. Attempts and cooldowns survive restart. Entry-window expiry still prevents late entry. Known capital/configuration/contract conflicts stop an entry; a never-dispatched exclusive-journal run can finish without requesting an expired product's position. Unknown/accepted order intents or recorded accepted orders prevent this shortcut. Existing client-order identities, fill accounting, reduce-only exits and subaccount transfer reconciliation remain in effect.

Reconciliation exhaustion preserves attention status, exposure records and uncertain capital/account reservations. It produces a manual-review diagnostic, a notification when configured and a private health count. Known open exposure remains observable from existing price streams without restarting failed order/position requests. This observation is not a new fill or settlement proof. Active strategies continue through the independent risk monitor. Fix the underlying issue, then use History's Resume recovery action to authorize another attempt budget. The authenticated `POST /api/strategies/{id}/recovery` requires `{"confirm":true}`, checks ownership, and rejects active/in-progress runs. A terminal run can resume only when it has an exhausted recovery record, such as pending subaccount release. It never blindly resubmits an unknown order. Existing subaccount release still proves the account flat and checks uncertain transfers before reuse.

Market broadcasts keep the same JSON message shape. Each publication is encoded once; the local depth dictionaries retain their existing sequence/coverage behavior while top-K selection avoids full-book sorting. CVD uses an incremental total, combines trades at an identical millisecond, and expires against wall-clock time. Main-analysis packet capture/caching, news orchestration, recheck rules, report wording and citation filtering are unchanged.

History uses chronological keyset pagination, including equal timestamps. The frontend retains already loaded pages across refresh and requests a complete attention count separately. Account overview reads all working-order pages. A healthy portfolio stream lets quiet refreshes request risk metadata without repeating exchange balances/orders/positions. The frontend tolerates older backends during rollout; recovery actions require an explicit server capability. Revision streams follow sign-in, token refresh and sign-out lifecycle changes.

ESLint excludes Python environments. Default backend pytest discovery includes news-agent tests. Unused frontend exports and the unused Lucide dependency were removed. Tested chart/materialization helpers and operational-script dependencies were retained.

Rollout steps:

1. Back up the Ubuntu database and record the currently deployed application image versions. Do not delete or rewrite previous migrations.
2. Build the updated trading backend and both market-data services using the existing Compose configuration and environment files. Deploy the trading writer first so migration 014 and the backward-compatible API additions are available, then the market services and frontend.
3. Verify private health shows both scheduler tasks running, recent risk completion, profile synchronization running and no unexplained recovery escalation. Verify existing owner identities were imported before relying on the local owner editor.
4. Confirm a harmless profile edit reads back immediately from Ubuntu and appears in Supabase after synchronization. A profile change is the only mirrored application data in this check.
5. Inspect historical attention runs before using Resume recovery. Verify original exchange-account assignment, journal outcomes, fills and transfer state. Deployment does not authorize a blanket retry or liquidation of historical positions.
6. Confirm a history older than 100 rows remains navigable and the complete attention count agrees with local records. Check live portfolio fallback and both public market feeds.

Development verification uses a separate PostgreSQL 17 container and private test network with dummy credentials, plus a second disposable database for ETH rollout tests. Source mounts are read-only. Browser checks use a loopback-only synthetic API that cannot place trades. No production migration, service restart, historical retry, position change or balance transfer is performed by this development workflow. Recorded test results and rollout status are in the implementation plan.
